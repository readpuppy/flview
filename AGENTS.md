# Repository Guidelines

## Project Structure & Module Organization

- `Cargo.toml` & `Cargo.lock` keep dependencies and metadata centralized; edit with `cargo` commands or `cargo add` when adding deps.
- `src/main.rs` chooses between the TUI (`src/tui.rs`) and web (`src/web.rs`) flows, keeping command parsing and dispatch logic on the main path.
- `src/fsutil.rs` and `src/hex.rs` house shared helpers (filesystem walking, previews). Add helpers here when both front ends need them, and keep them stateless.
- Place new modules inside `src/`, keeping one public API surface per file and re-exporting from `main` if needed.
- The `target/` directory is generated by Cargo; do not commit it.

## Build, Test, and Development Commands

- `cargo run -- tui`: builds and launches the terminal UI using the current directory as root; useful for manual navigation checks.
- `cargo run -- web --addr 127.0.0.1:8080`: starts the web UI server; visit `http://127.0.0.1:8080/` to verify browser behavior.
- `cargo fmt`: formats all Rust source files according to the Rust style guide; run before submitting code.
- `cargo clippy -- -D warnings`: enforces clippy lints with warnings treated as errors.
- `cargo test`: executes the test suite, including unit tests declared inline.

## Coding Style & Naming Conventions

- Stick to standard Rust naming: `snake_case` for functions/variables, `UpperCamelCase` for structs/enums, `CONSTANT_CASE` for constants.
- Use 4 spaces per indentation level, no tabs, and keep line widths under ~100 characters.
- Prefer short, focused modules; each file should expose a minimal public API and keep implementation details private.
- Always run `cargo fmt` before committing and fix `clippy` warnings unless a deviation is documented inline.

## Testing Guidelines

- Tests are inline with the code they cover using `#[cfg(test)]` modules; add `tests/` only for integration suites.
- Name tests descriptively, e.g. `fn list_dir_returns_entries()` or `fn web_mode_blocks_outside_root()`.
- Run `cargo test` locally after modifying logic, especially filesystem helpers shared between UIs.

## Commit & Pull Request Guidelines

- Use imperative commit messages (e.g., “Add hex preview helper”). Mention the module/feature in the message body if needed.
- PRs should describe what changed, why it matters, and how it was verified; link related issues and include manual test steps (screenshots optional for UI changes).

## Configuration & Notes

- Pass `Path`/`PathBuf` explicitly when adding new helpers so both UIs can reuse them without hidden globals.
- Document any new CLI flags in both `README.md` and the relevant module to keep usage consistent.
